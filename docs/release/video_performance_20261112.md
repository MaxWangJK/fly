# 视频播放与关闭后卡顿修复

用户反馈：在“门 / 木门 / 安装视频”导入MP4后可以播放，但播放时与关闭后，切换目录和其他功能均变慢。本轮用临时文件、内存数据库及独立原生测试程序排查，没有打开用户实际视频或业务库。

## 原因与改动

1. 本地同步每2秒执行一轮，一轮中上传前、下载阶段均遍历文件。原代码每次都读取本机文件的全部字节计算SHA-256；异步读取并不把摘要计算移出界面线程。大视频会反复争用CPU和磁盘，这项工作独立于播放器，关闭视频后仍可继续。
   - 新增进程内校验缓存，依据路径、大小、修改及变更时间复用已验证摘要，不因播放改变访问时间而失效。512条上限，文件有变化或满5分钟审计周期后重新计算。
   - 完整摘要放入后台isolate，局域网接收完成校验也移出界面线程。新下载强制完整校验；校验时文件发生变化会重试一次，持续变化则报错，不把混合内容认作有效。文件内容、摘要算法、同步协议与数据库结构保持。
2. 播放进度或缓冲事件原本直接重建整个播放器，包含视频纹理子树。复现测试中，100次位置更新产生100次画面子树构建。
   - 视频画面使用独立的稳定RepaintBoundary子树；时间显示约每250ms更新，播放、音量及错误等操作状态立即响应，拖动进度不受此间隔限制。100次进度更新不再重建视频画面。
3. 原退出流程直接异步dispose，没有先停止解码。补查还发现报错会清除控制器的初始化标记，普通pause可能无法继续传至底层。
   - 关闭/后台/外部打开前暂停；底层释放保护在dispose前按播放器ID暂停，报错后也有效。失败立即释放，重试等待旧资源释放，初始化中关闭会取消界面超时等待，避免晚到回调影响已退出页面。
   - Windows诊断日志由全量转为警告/错误，减少原生日志转发到Dart的工作；原解码器和画质策略保持。沿用已锁定的播放器接口6.9.0，仅从测试依赖调整为运行时依赖，没有升级包或SDK，也没有修改全局缓存源代码。

## 验证

43项不同的相关用例通过：13项媒体查看器、4项摘要缓存、10项文件点击/拖放、2项已有文件同步、2项传输调度、10项断点续传/局域网恢复，以及真实HTTP的双设备文件传输和三设备合并两项。最后两项起初缺少本机测试后台而跳过，随后启动临时后台重新运行并通过；没有把跳过算作通过。全项目静态检查无问题，未重跑整套客户端或后台测试。

缓存测试覆盖同大小外部修改、删除、审计过期、并发去重、容量限制、失败后重试、读取过程中变更，以及连续上传/下载/轮询只完整读取未变文件一次。实际局域网双向传输包含20MiB文件；下载仍验证全部内容和大小。

64MiB合成文件的AOT测试连续校验4次，原逻辑完整读取4次约4105ms，新逻辑后台读取1次并复用3次约1012ms；该次界面计时器最大间隔约40ms与17ms，摘要完全一致。[原始结果](../handoff/windows/20261112-build60/hash-ui-aot-check.json)。这是单次隔离测量，不能作为所有设备、视频或文件库规模的性能保证。

最终真实Windows播放器以官方1280×720样例连续播放/关闭3轮，进度、退出及后续界面心跳均完成，无播放或退出异常。[资源诊断](../handoff/windows/20261112-build60/native-playback-resource-check.json)。该程序使用Debug模式，保留原始CPU/内存数据供复查；不把JIT预热、系统负载下的数值解读为发布版帧率结论，也不据此声称所有视频都没有原生资源问题。

用户的原MP4、实际数据目录与设备组合未读取或复测；Android完成编译和签名检查后仍由用户实机验证。Windows与Android交付见[build60](fly_2_0_24_build60.md)。SQLite20、后台0005、原书籍配置和原签名保持；云同步仍不传实体文件。
